# 第四阶段总计划

## 1. 阶段目标

在已经跑通的 LangChain/LangGraph、Tool Gateway、Evidence、PostgreSQL Checkpoint、
Memory/Context、异步 Job 和 SSE 基础上，把项目扩展为一个可复现、可解释、能处理更多股票分析
任务的受控 Agent 系统。

本阶段只分四个完整 Step。执行时一次只实现一个 Step，审核通过后再进入下一步。

## 2. 执行顺序

| Step | 主题 | 核心结果 | 依赖 |
|---|---|---|---|
| 01 | 正确性、评测与 Git 基线 | 先修 P0 语义/证据缺陷，建立冻结环境和安全可交付仓库 | 当前系统 |
| 02 | 知识、RAG、记忆与上下文 | 建立外部知识流水线、混合检索和分层记忆闭环 | Step 01 |
| 03 | 分析工具、Skill 与受控循环 | 增加技术/基本面/截面/因子/事件分析，开放一次受控修正 | Step 02 |
| 04 | 多租户并发、交付与互操作 | 请求准入、租户隔离、并发 Worker、可选只读 MCP、薄 UI 与总验收 | Step 03 |

## 3. 模型策略

- 项目默认模型统一为正式版 `deepseek-v4-flash`；
- Planner、Report、Reviewer、上下文摘要和评测默认均使用 Flash；
- Pro 仅保留为显式实验覆盖值，不用于自动路由、默认配置或失败回退；
- 历史 Pro 测试文档和产物保留，但必须明确属于历史基线；
- 每次模型调用记录模型 ID、Prompt/Skill 版本、Usage、耗时和终态。

## 4. 测试节奏

遵循“Step 内少测、Step 尾集中验证”：

- 子模块实现时只运行一个最小冒烟或关键确定性检查；
- 一个 Step 的所有功能完成后，再统一运行专项测试、全量回归、真实 Flash 测试和修正；
- 修正后只重复受影响用例与最终 Gate，不进行无信息增量的反复全量测试；
- 网络不稳定时保留完整题目、输入、原始输出、重试记录和失败分类到 Markdown/JSON；
- 供应商错误和网络错误使用有限指数退避，不把重试当作模型质量修复。

## 5. 统一验收原则

- P0 安全、越权、错误实体/时间/量纲、伪造引用必须 100% 通过；
- Intent、Skill、Tool、参数、Evidence 覆盖、引用和 Budget 闭合目标为 100%；
- 含模型变体的综合题集总体通过率不低于 95%，失败题必须分类并给出修复/豁免理由；
- 公式、日期、时点、去重、权限和状态机使用确定性测试，不交给 LLM Judge 决定；
- 真实模型评测使用私有 Holdout，并与开发回归题分离；
- 记录成功率之外的轨迹重复率、无效 Tool 调用、恢复率、P50/P95 延迟、Token 和成本。

## 6. 每步交付形式

每个 Step 必须产出：

1. 更新后的设计或数据说明；
2. 可运行代码与必要迁移；
3. `PROGRESS.md` 中的任务、问题和决定；
4. 失败用例原始输出；
5. Gate 报告和可复现命令；
6. 对 README、Compose、`.env.example` 和操作手册的同步更新。

## 7. 变更控制

以下情况必须暂停并回到方案审核：

- 数据源无法稳定提供所需来源、发布日期或时点字段；
- 为实现功能必须开放任意代码、SQL、交易或外部写权限；
- 新组件明显超过当前 Docker 资源预算；
- 需要从一次受控修正扩大为开放循环或多 Agent；
- 因子定义或财务时点口径无法给出可验证公式和来源；
- GitHub 发布可能包含 API Key、受版权保护的 PDF/研报或不可公开数据。
