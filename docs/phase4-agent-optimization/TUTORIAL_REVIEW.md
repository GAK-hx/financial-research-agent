# Agent 教程结论与项目映射

## 1. 阅读范围

本计划基于以下两份教程版本进行交叉阅读：

- 英文 v1.3：`2606.24937v2.pdf`，包含新增的 Loop Engineering 章节；
- 中文 v1.0.3：`agentic-ai-guide-zh-v1.0.3.pdf`，用于核对中文概念和整体脉络。

重点阅读了 RAG、记忆、Harness、循环工程、Agent 设计模式、环境、MCP、Skills、
多 Agent、框架、Agentic UI 和评测章节。英文新版比中文版本多出的循环工程，是本次计划
增加“证据充分性检查、一次受控修正、进展判断与终止条件”的主要依据。

## 2. 对本项目最重要的判断

### 2.1 当前框架方向正确，不需要重写

教程把 Agent 系统拆成知识、记忆、运行框架、循环、环境和评测等层。项目当前使用
LangChain 标准化接口、LangGraph 管理状态与恢复，并用自有 Gateway 和 Evidence 做
金融约束，已经落在合理架构上。下一阶段应补能力和验证闭环，而不是再换一次框架。

### 2.2 Harness 不是另一个 Agent 框架

Harness 是模型之外的运行控制层，负责：

- 限制模型可见和可调用的 Tool；
- 校验参数、规范化结果和错误；
- 管理调用次数、Token、费用、并发和超时；
- 保存状态、Checkpoint、证据、Trace 与恢复信息；
- 判断是否有进展、是否需要修正以及何时终止。

LangGraph 承载状态流转，现有 Gateway、Policy、Budget、Context、Memory 和 Validator
共同构成项目 Harness。两者是组合关系，不是二选一。

### 2.3 工作流优先，有限自主性比开放 ReAct 更合适

金融分析要求范围、口径和来源可复核。正常请求继续走确定性的 Plan-and-Execute；仅当
证据充分性检查明确指出缺失时，允许一次受控修正。修正不得扩大股票、时间范围、分析意图
或 Tool 权限。这样既增加 Agent 处理变体问题的能力，又不会变成不可控的开放循环。

### 2.4 验证器就是运行循环的“反馈信号”

当前报告校验已有基础，但还缺少原问题到结构化 QuerySpec 的语义对齐。例如“最近一个
完整交易月”不能只检查最终日期格式，还必须验证解析后仍保持“月”的量纲。后续验证顺序为：

1. 确定性规则检查范围、单位、日期、实体、公式和引用；
2. 证据充分性检查发现缺项；
3. 最多执行一次受控修正；
4. 仍不充分时给出限制和部分结果，而不是编造完整答案；
5. LLM Judge 只作为辅助评测，不替代确定性检查。

### 2.5 知识、记忆和上下文必须分开

| 层 | 本项目含义 | 主要存储 | 关键约束 |
|---|---|---|---|
| 知识 | 公告、新闻、研报和事件等外部事实 | Iceberg + PostgreSQL 元数据 + Milvus 索引 | 来源、时间、版本、状态可追溯 |
| 工作记忆 | 当前 Run 的问题、计划、Tool 结果和进度 | LangGraph Checkpoint | 有预算，可恢复，不覆盖原始证据 |
| 情节记忆 | 已验证的失败、修正策略和任务结果 | PostgreSQL | 只有通过验证的信息才能写入 |
| 语义记忆 | 稳定实体关系和事件事实 | 知识层，而非用户会话 | 有时效、冲突与来源治理 |
| 程序记忆 | Skill 的流程、Prompt、Tool 与校验规则 | 版本化 Skill 包 | 发布审核，模型不可自行激活 |
| 偏好记忆 | 用户明确确认的展示与分析偏好 | PostgreSQL | 用户/租户隔离、TTL、可删除 |

Context Builder 只负责从上述层选择本轮所需内容，并不拥有事实。压缩只能生成模型视图，
不能覆盖 Evidence、数值和 Source Locator。

### 2.6 不需要自研 KV Cache

KV Cache 是模型推理服务内部对历史 Token 的注意力 Key/Value 缓存。客户端项目通常不能
直接管理 DeepSeek 服务端 KV 数据。本项目可做的是：稳定系统 Prompt 和 Tool 定义的前缀、
减少无意义变化、复用服务商支持的前缀缓存，并用 API Usage 校准 Token 估算。Context
压缩解决的是“发送什么”，KV Cache 解决的是“相同前缀如何少算”，两者互补但不是一层。

### 2.7 当前 Skill 更像配置，需要升级为能力包

教程中的 Skill 不只是名称和 Tool 白名单，而是可版本化的能力包：

- Manifest 与适用条件；
- Prompt、参考资料和示例；
- Tool 绑定与参数约束；
- 工作流、预算和终止规则；
- Evidence 要求和输出 Validator。

现有 `concise`、`risk` 更适合作为报告 Profile；技术分析、基本面、截面筛选、因子研究、
事件影响和综合分析才是独立 Skill。

### 2.8 MCP 适合作为外部边界，不适合内部重写

内部 Tool 已经使用 LangChain `StructuredTool` 并经过统一 Gateway，不需要改成 MCP 才算规范。
当项目需要给外部 Agent 或客户端复用稳定能力时，可增加只读 MCP Adapter，并让所有请求继续
经过相同 Policy、Budget、Evidence 和审计链。现阶段不需要 A2A 或多 Agent 团队。

## 3. 教程观点与项目决策

| 教程主题 | 当前基础 | 主要缺口 | 本阶段决策 |
|---|---|---|---|
| RAG | PDF、BGE、Milvus、Retriever | 固定分块、纯向量、增量治理弱 | 结构化父子分块、混合检索、版本删除和独立评测 |
| Memory | Session、Preference、Checkpoint | 情节/程序记忆薄，知识与记忆边界不完整 | 建立分层写入、冲突、TTL、反思和清理策略 |
| Harness | Gateway、Policy、Budget、Validator | 缺少进展检测和语义对齐 | 加入受控修正、无进展检测和完整终止条件 |
| Loop | 固定计划、`replan=0` | 变体问题恢复能力有限 | 只允许证据驱动的一次修正 |
| Skills | 声明式 Registry | 能力内容浅，Profile 与 Skill 混用 | 升级为版本化能力包和动态 Tool 可见性 |
| Environment | Docker、测试集、模型评测 | 生产日期被冻结、Holdout 管理不足 | 生产/评测时钟分离，冻结数据快照和私有 Holdout |
| Evaluation | 确定性指标、真实模型测试 | 缺少轨迹效率、RAG 和记忆专项指标 | 分层评测，确定性优先，Step 尾集中运行 |
| Framework | LangChain + LangGraph | 无需替换 | 保持基础框架，突出金融增强层 |
| UI | FastAPI、SSE | 中间过程展示较弱 | 可选薄 UI 展示计划、证据、风险、恢复和取消 |
| MCP | 暂无 | 外部互操作边界缺失 | 最后一步增加可选只读 Adapter |

## 4. 对“功能是否过于单一”的结论

当前项目并非框架太受限，而是领域 Tool 和 Skill 还少。正确扩展顺序是先补确定性的分析引擎、
事件知识和更真实的 Skill，再开放一次有限修正；不应先放开任意代码执行或无限 ReAct。
Agent 的能力来自可组合、可信的工具和反馈循环，不来自允许模型随意操作基础设施。
