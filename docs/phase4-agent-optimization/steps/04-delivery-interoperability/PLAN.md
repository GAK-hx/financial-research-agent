# Step 04：多租户并发、交付、互操作与演示

## 1. 目标

把前三步能力整理成支持多用户并发查询、可部署、可观察、可演示、可安全上传 GitHub 的完整
项目，并以最小成本提供外部 Tool 互操作边界。

本步优化的是应用服务层并发：请求准入、任务排队、Worker 调度、租户隔离、连接池和过载保护。
当前使用托管 DeepSeek API，不在客户端实现 PagedAttention、连续批处理或 KV Cache；这些属于
模型服务提供方的推理层职责。

## 2. API、Job 与运行体验

- 复用 FastAPI、Job API、Worker、PostgreSQL 领取、SSE 和 LangGraph Checkpoint；
- API 响应保持稳定版本，并补充计划、Skill、Context/Evidence Manifest、修正次数和终止原因；
- SSE 展示计划生成、Tool 开始/完成、Evidence 增量、证据缺口、受控修正、报告校验和终态；
- 支持取消、断线重连、断点恢复和部分失败；
- 错误按用户输入、数据缺失、权限、预算、供应商、网络、解析和系统错误分类；
- 失败输出对用户可理解，内部 Trace 保留完整技术原因并脱敏。

## 3. 多租户并发与过载保护

### 3.1 身份与隔离边界

- 由认证层生成可信 `tenant_id`、`user_id` 和角色，不接受用户在业务请求中任意声明身份；
- Run、Event、Checkpoint、Memory、Artifact、Evidence 和审计查询都带租户隔离条件；
- 管理接口与普通分析接口分权，跨租户访问默认拒绝并留下脱敏审计；
- PostgreSQL 行级安全是否启用由实现期 Spike 决定，但 Repository 层租户过滤是必需项。

### 3.2 请求准入、配额与公平性

- 增加全局、租户和用户三级并发上限，并分别限制排队任务、模型调用、Tool 调用和 Token/费用；
- 对共享 DeepSeek 账号/API Key 建立进程间统一速率预算，识别 `429` 和 `Retry-After`；
- 交互式查询优先于离线批处理；同优先级使用公平调度，防止单一租户占满全部 Worker；
- 所有拒绝都返回明确的 `429` 或 `503`、原因、可重试标记和建议等待时间；
- 幂等请求在重试时返回已有 Run，不重复占用队列或产生副作用。

### 3.3 执行与资源控制

- 保留 PostgreSQL 原子领取、Lease、Checkpoint 和结果复用，先通过实测验证现有队列；
- Worker 设置有界并发，不让单个 Run 内的并行 Tool 调用突破全局或租户额度；
- 为 DeepSeek、PostgreSQL、Milvus、Iceberg/本地分析和外部数据源分别设置连接池、Semaphore、
  超时和熔断边界；
- Worker 缩容或退出时停止领取新任务，完成、转移或安全释放当前 Lease；
- 队列深度、最老任务等待时间、活跃 Worker 和 Provider 限流率作为扩缩容信号。

### 3.4 队列升级条件

第一版不因为“并发”直接引入 Redis/Celery。只有同时满足以下条件才重新选型：

1. 冻结负载下 PostgreSQL 领取/状态写入成为可复现瓶颈；
2. 调整索引、批量写入、连接池和 Worker 参数后仍不能达到目标；
3. 新队列能明确改善吞吐、延迟或公平性，且不会形成两套状态真相。

即使升级消息队列，PostgreSQL 仍保存 Run、Checkpoint、预算、审计和唯一终态；消息只承担调度，
不能成为不可回放的唯一业务状态。

### 3.5 并发验证

- 使用确定性 Stub/冻结数据完成 1、10、30、50 虚拟用户分级压测，隔离模型网络波动；
- 使用 Flash 做小规模真实并发端到端验证，严格限制费用和调用次数；
- 分别记录 API 接收延迟、队列等待、首个 SSE 事件、执行时间和总完成时间，不把模型延迟误算成
  Web API 性能；
- 验证跨租户泄漏、重复领取、重复终态、预算超限、丢失 Run 均为 0；
- 验证达到配置上限后的请求被明确拒绝或延后，而不是无限排队或拖垮数据库；
- 输出 P50/P95/P99、吞吐、错误率、Provider 429、连接池等待和 Worker 利用率。

## 4. 可选只读 MCP Adapter

MCP 不替换现有 LangChain Tool，而是一个外部协议适配层：

```text
MCP Client → MCP Adapter → 原有 Tool Gateway
           → Policy → Budget → Domain Tool → Evidence/Audit
```

约束：

- 默认关闭，使用独立 Docker Profile；
- 首批只暴露稳定、只读、幂等 Tool；
- Tool Schema 与内部领域模型共享，避免维护两套参数定义；
- 声明 read-only、idempotent 和外部访问特性；
- 每个请求必须有调用方、Run、权限、预算和审计记录；
- 不开放 sampling、A2A、任意网络、任意 SQL、代码执行或交易 Tool；
- MCP 不成熟或无实际外部消费者时，可以只交付经过验证的 Adapter Spike，不阻塞主系统上线。

## 5. 可观测性与回放

- 统一 Trace ID、Run ID、Node Attempt、Model Call、Tool Call 和 Evidence ID；
- 记录模型、Prompt、Skill、Tool、数据快照和 Validator 版本；
- 统计成功率、恢复率、轨迹长度、重复动作、无效 Tool、Token、费用、P50/P95 和错误分类；
- 增加租户维度的排队深度、准入拒绝、并发占用、Provider 限流和连接池等待指标；
- 提供脱敏 Trace 回放，能从冻结数据重现计划、Tool 和验证路径；
- OpenTelemetry 作为可选导出，不为了展示增加重型监控集群。

## 6. 薄演示界面

界面只服务演示和调试，不构建复杂前端平台。至少展示：

- 问题、股票、时间范围、Skill 和运行状态；
- 当前计划及每步完成情况；
- Tool 调用、参数摘要、耗时和错误；
- Evidence 列表、来源、数据截止日和引用；
- 证据缺口、是否发生受控修正及原因；
- 报告、风险向量、数据限制、取消和恢复入口。

具体技术选型在实现前用最小 Spike 比较；可复用现有 SSE，不引入独立消息中间件。

## 7. Docker、GitHub 与文档

- 从干净克隆通过 Docker Compose 启动 PostgreSQL、Milvus、App、Job 和所需批任务；
- 常驻服务设置适度资源限制，重型索引/批任务使用 Profile 按需运行；
- API 与 Worker 可独立扩容；默认 Compose 参数保持开发机可运行，并提供并发演示覆盖值；
- `.env.example` 不含 Key，启动前检查必填项；
- API Key、运行产物、Lake、缓存、第三方 PDF/研报不进入 Git；
- 私有 GitHub 完成 CI 后，再根据版权和许可清单决定是否公开；
- README 提供架构、数据边界、快速演示、评测结果、已知限制和简历可解释的实现要点；
- 历史 Pro 评测保留为旧基线，当前演示和最终结果统一使用 Flash。

## 8. 最终验收

一次集中执行：

1. 干净克隆和 Docker 构建；
2. 数据初始化、知识更新、因子批处理和索引；
3. 多租户身份、准入、配额、公平调度、过载拒绝和资源隔离；
4. 同步/异步 API、SSE、取消、恢复和部分失败；
5. 冻结 Stub 分级并发压测与小规模真实 Flash 并发验证；
6. 六类 Skill 的私有 Holdout 和多次稳定性测试；
7. RAG、Memory、Context、Factor、Evidence 和受控修正专项；
8. 可选 MCP 兼容、权限和审计测试；
9. Secret、依赖、许可证、版权和资源扫描；
10. 演示脚本完整走查。

模型评测默认全部使用 `deepseek-v4-flash`。网络失败保存原始输出并按有限指数退避重试；供应商
不可用不算业务正确性失败，但必须单独报告，不能用规则输出伪装成真实模型通过。

## 9. Gate

- 干净克隆可按文档启动并完成核心演示；
- Run 可取消、恢复和回放，终态与预算一致；
- 配置的全局/租户/用户并发上限不可被竞态突破，过载响应明确且可观测；
- 冻结并发集中的跨租户泄漏、重复执行、重复副作用、预算超限和丢失 Run 均为 0；
- API、队列、Worker、Provider 和存储延迟分别统计，给出目标容量而非笼统宣称“高并发”；
- P0、安全、引用和权限指标 100%；
- 真实 Flash 私有综合题集不低于 95%；
- MCP 如启用，不可绕过 Gateway，越权和副作用为 0；
- Git 历史和当前树不含 Secret、私有数据或无权分发的 PDF/研报；
- 文档明确当前能力、数据口径和未实现项，不夸大实时、时点回测或自动交易。

## 10. 停止条件

- 需要公开敏感 Key、私有数据或版权材料才能演示；
- MCP 或 UI 迫使内部 Tool 维护第二套业务逻辑；
- 干净环境仍依赖开发者机器的绝对路径或相邻项目；
- 最终评测无法冻结数据/Prompt/Skill/模型版本；
- 关键 P0 失败被总体 95% 阈值掩盖；
- 为提高表面吞吐而绕过租户隔离、Budget、Evidence 或 Validator；
- 未经基准证明便同时维护 PostgreSQL Queue 与第二套任务状态。
